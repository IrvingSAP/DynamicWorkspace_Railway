Cómo funciona el contrato HTTP

El contrato es el patrón común de todas las llamadas de jobs: kind, proyecto o pipeline, wait, estados de máquina y el JSON de respuesta (ok, job_id, errors[], artifacts). Gate, Pipe o Split cambian el archivo y el summary; el envelope no.

Esta página describe el flujo de lectura para alinear al integrador. La pantalla Contrato muestra el catálogo vivo; el ? de esa vista es la ayuda contextual. No ejecuta jobs.

Ruta rápida

  1. Separe qué (kind + slug o pipeline) de espera (sync / async).
  2. Valide metadatos con POST /jobs/validate (sin archivo si no hace falta).
  3. El catálogo máquina: GET /api/v1/contract con Bearer.

Qué es el contrato

Es la forma HTTP de PLATFORM API: un solo patrón para todos los kind ejecutables. El integrador no inventa un endpoint por app.

En una frase

La gramática del request y de la respuesta. Ejecutar el runner es POST /api/v1/jobs/run (otra pantalla / otro paso).

Qué ve US en pantalla

  • Tabla de kinds (app, archivos, scope, wait por defecto, si está cableado).
  • Estados de job, veredicto Gate y pasos de pipeline.
  • Paths de validate, contract, run y openapi.
2

Cuál es la función de Contrato

Función principal: congelar cómo se nombra el trabajo y cómo se lee el JSON, para que Postman, curl y el ERP no divergjan del código.

Problema que resuelve

  • Un path distinto “de producto” por cada app.
  • Confundir wait (sync/async) con job vs pipeline.
  • Tratar un rechazo Gate como error HTTP 4xx cuando es 200 + ok: false.

Qué ganas

  • Validate sin disparar el motor (comprueba kind, slug, wait).
  • Catálogo vivo con Bearer: mismos kinds que la UI.
  • Repair / Profiler en catálogo pero no ejecutables todavía.
3

Qué no es (y qué sí usar en su lugar)

Contrato no…

  • No crea clientes ni emite keys (eso es Clientes).
  • No lista cada URL con ejemplos de curl (eso es Paths).
  • No mapea runner Django por kind (eso es Integración).
  • No sube el archivo de negocio ni parte un TXT.

Usa otra pantalla si…

  • Clientes — identidad y Bearer.
  • Paths — índice canónico de métodos.
  • Seguridad — tamaño, tasa, TTL.
  • Apps UF — publicar el project_slug que irá en el run.
4

Dos ejes (no mezclar)

EjeCamposSignificado
Qué kind + project_slug Job suelto de un proyecto publicado.
Qué (cadena) kind=file_pipeline + pipeline_id Cadena publicada. No mezcle slug de job suelto con pipeline_id.
Espera wait=sync | async 200 al terminar vs 202 y luego GET del job. Distinto de “es un pipeline”.

Atajo: mode=pipeline equivale a kind=file_pipeline. El default de pipeline en contrato es async.

5

Flujo de trabajo

Camino de alineación: leer UI → validate → contract HTTP → recién entonces run.

  1. US abre Contrato y cruza kinds con el proyecto que UF publicó (slug real).
  2. La máquina hace GET /api/v1/whoami y luego GET /api/v1/contract.
  3. POST /api/v1/jobs/validate con kind, slug y wait (form-data; sin file si solo prueba metadatos).
  4. Si validate es 200, el run lleva archivo e Idempotency-Key.

7

Casos típicos

  • Validate 400 «Kind no reconocido» — el body no es form-data o el kind está mal escrito.
  • HTML 404 en /j/api/v1/… — sobra una letra en la URL; el contrato vive bajo /api/v1/….
  • Split: validate y contract listan file_split; el output único puede no existir (varias partes).

Cómo funcionan los clientes de máquina

Un cliente API es la identidad de un sistema externo (ERP, RPA, middleware) que llama a DynamicWorkspace por HTTP. No es un usuario UF: no entra con 2FA. Usa un Bearer (dw_test_… o dw_live_…) ligado a esta compañía y a unos scopes explícitos.

Esta página describe el flujo completo del recorte Clientes. En el listado y la ficha también hay ayuda contextual (botón ? / Ayuda) con el detalle de esa vista.

Ruta rápida

  1. Alta del cliente, copie la key una vez al cofre.
  2. Marque scopes y (si aplica) política de proceso.
  3. Pruebe whoami / run; rote o revoque cuando cierre el sandbox.

Qué es un cliente de máquina

Es el registro que PLATFORM API usa para saber quién llama: código (p. ej. api-qa-p01), entorno sandbox o producción, scopes y estado activo o revocado. La key se emite al alta o al rotar; cada POST /jobs/run reutiliza el mismo Bearer.

En una frase

Una identidad de integración por compañía: no es un proyecto File Gate ni un pipeline; es la credencial para ejecutar lo que UF ya publicó.

Resultado que entrega

  • Key visible una sola vez (pantalla Key emitida).
  • Listado y ficha para editar nombre/scopes sin cambiar el secreto.
  • Auditoría append-only (alta, rotación, revocación).
2

Cuál es la función de Clientes

Función principal: dar de alta y gobernar las keys que autenticarán /api/v1/…. El trabajo de negocio (partir un archivo, validar, un pipeline) lo hacen las apps; el cliente solo identifica y autoriza a la máquina.

Problema que resuelve

  • Un ERP no puede usar la cookie de sesión US/UF.
  • Hace falta un Bearer por entorno (sandbox ≠ producción).
  • Hay que rotar o dar de baja sin borrar el historial de jobs.

Qué ganas

  • Scopes mínimos (no un token dios).
  • Aislamiento por compañía: no ve jobs de otra.
  • Rotar la key no cambia el job_id de corridas ya hechas.
3

Qué no es (y qué sí usar en su lugar)

Clientes no…

  • No diseñan esquemas, mapeos ni pasos de pipeline.
  • No sustituyen Contrato, Paths, Integración ni Seguridad (otras entradas del menú).
  • No “des-revocan”: hay que crear otro cliente.

Usa otra pantalla si…

  • Contrato / Paths — catálogo HTTP y kinds.
  • Seguridad — tamaño, tasa, TTL, allowlist de webhooks.
  • Auditoría — ciclo de vida del cliente, no el detalle de un job.
  • Apps UF — publicar el proyecto que la máquina va a disparar.
4

Flujo de trabajo

Camino fijo: crear → copiar key → probar HTTP → rotar o revocar.

  1. US → API → Clientes → Nuevo cliente (código, entorno, scopes).
  2. Copie el Bearer en el cofre. No recargue Key emitida sin haber copiado.
  3. GET /api/v1/whoami y, con proyecto publicado, POST /jobs/run.
  4. Si se filtra o caduca la política: Rotar key (la anterior da 401).
  5. Al cerrar el integrador: Revocar. Los jobs ya corridos siguen en el historial de la app.

Scopes

La máquina no hereda el rol PA/GE. Cada permiso se marca en la ficha y se guarda.

ScopePermite
jobs:runDisparar un job suelto (POST /jobs/run)
jobs:readDetalle, listado, estado
jobs:cancelCancelar si el runner lo admite (Split completed → 409)
pipeline:runCadena publicada
artifacts:downloadInforme y archivo de salida

Casos típicos

  • Sandbox de QA: un cliente dw_test_… para Postman o curl.
  • Producción: otro cliente (otro código o mismo código en entorno prod) con dw_live_….
  • Key filtrada en un chat: rotar; no crear un segundo cliente “por si acaso” si sigue siendo el mismo integrador.

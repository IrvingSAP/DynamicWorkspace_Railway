Ayuda — Mapa de integración

Cómo encaja File Watch con Scheduler, Pipeline, la API y los procesos de Railway. No se configura nada aquí.

← Volver al mapa

Propósito de la página

Es una referencia de la compañía: Watch detecta y materializa; Scheduler reclama por watch_id (el código de la bandeja). El runner es el mismo que UI y PLATFORM API.

  • CRUD de bandejas no está en la API de máquina en el MVP. El push de archivo es el endpoint de la bandeja (Origen API).
  • File Gate no configura rutas IFS: viven en Origen de Watch.
  • Artifact (hash fijo en el plan) ≠ Watch (código de bandeja; cada llegada otro hash).

Sección Capas

De izquierda a derecha: de dónde llega el archivo hasta el reloj del plan.

Capa (en el mapa)PreguntaDueño
De dónde ¿SFTP / carpeta / API push? File Watch · Origen
Qué archivo ¿Lote + hash en storage? File Watch · Intake
Hacia qué runner Job / pipeline / diferir File Watch · Enrutado
¿Cuándo encolar? Al llegar vs solo pending File Watch · Disparo
Cuándo (reloj) Cron del plan con watch_id File Scheduler

Sección Canales

Cuatro formas de llegar al mismo runner. La columna Código es el identificador del canal, no un error.

CanalQué haceCódigo
UI Ejecutar Una persona lanza un Job o un pipeline_run. ui
PLATFORM API POST de máquina (Bearer). No da de alta bandejas en el MVP. api
File Watch Llegó el archivo: fire al llegar o lote Pendiente. watch
File Scheduler Claim del lote por código de bandeja. scheduler

Bridge Scheduler

ReglaDetalle
Destino del plan input_origin=watch + código de bandeja = slug de la bandeja (se elige en el plan Destino).
Tick Claim atómico → entrega hash y storage al runner. Pista: claim_pending_batch(company, watch_slug, …)
Sin Pendiente El tick responde schedule_missing_input (código Scheduler, no watch_*). No inventa archivo.

Railway

PiezaRolProceso
Web Django CRUD de bandeja, lotes, auditoría, avisos, este mapa. web
Worker Watch Poll de origen, intake y fire o pending. watch
Worker Scheduler Claim pending por watch_id → mismo runner. scheduler
